## F-t5-L3-1: Login holds a DB connection while queued for argon2 slots

`login` opens a tx and runs `SELECT ... FOR SHARE` before awaiting `password::verify`, which waits on a 4-permit semaphore. Concurrent unauthenticated logins, including unknown emails, each pin a pooled connection while queued, so a small flood can exhaust the sqlx pool and starve authenticated routes.

**Recommendation:** Read the row without a held tx, verify, then open a tx that re-checks `password_hash` unchanged under `FOR SHARE` before inserting the session. Alternatively acquire the semaphore before `pool.begin()`.

## F-t5-L3-2: accept_invite holds user row lock and a connection across hashing

The tx holds the `users FOR UPDATE` lock and a pooled connection while `password::hash` waits on the semaphore and runs argon2. Concurrent accepts, logins for that user and CLI resets are blocked for that whole time, and the 401 path for a bad token also takes a connection.

**Recommendation:** Hash the password after validating the length but before `pool.begin()`. The 'no hashing on reuse' requirement then needs a cheap non-locking pre-check of the invite, which the first SELECT already provides.

## F-t5-L3-3: No per-account or per-IP login throttle

Only a global concurrency cap exists, so passwords can be guessed online without limit. The code comment defers this, but AC-1 and the CLI-only invites model do not state that deferral.

**Recommendation:** Record the deferral in docs/DECISIONS.md with a trigger, or add a simple in-memory failure counter per email.

## F-t5-L3-4: Tombstone log emitted after commit can be lost

`reset_password` logs `event=tombstone` after `tx.commit()`. A crash or log failure between the two loses the log line, though the table row survives.

**Recommendation:** Accept as is, since the table is authoritative, or state in the docs that the table is the source of truth.
